Chapter 12 — Benchmarking and Reproducible Quantum Experiments

Chapter purpose. Build enough conceptual and mathematical understanding to predict an experiment before running it. The projects below are applications of the chapter, not substitutes for the theory.

1. A benchmark begins with a question

A useful benchmark defines a scientific question, circuit family, metric, controls, and stopping rule before inspecting favorable results. A single vendor dashboard score or screenshot is not a reproducible experiment.

2. Metadata is experimental data

Backend identity, date/time, calibration context when available, logical circuit, transpiled circuit, compiler version/settings, mapping, shots, job identifiers, software versions, and raw counts can all affect interpretation. Preserve them.

3. Uncertainty and drift

Shot noise creates statistical uncertainty, while hardware calibration and environmental behavior can change over time. Repeated runs at different times may therefore differ even when source code is unchanged.

4. Reproduction and extension

Reproduction asks whether a stated baseline can be obtained independently. Extension changes a justified variable or method to answer a new question. OQCL's capstone separates these stages so students cannot hide a failed reproduction behind an unrelated modification.

5. Cost-aware science

Hardware time and credits are experimental resources. Students should estimate circuits × shots × jobs before execution, use simulators for debugging, and record actual resource use. Cost optimization is part of experimental design, not merely administration.

Instructor teaching layer

Use case: doing quantum computing as experimental science

Reproducibility turns a circuit run into evidence. Students learn to preserve raw counts, compilation settings, backend identity, shots, software versions, dates, metrics, and limitations. This prepares them for research rather than screenshot-based demonstrations.

Problem: device results drift and cost resources

QPU calibration changes, queues vary, and additional shots cost time or credits. A scientifically responsible workflow debugs on simulators, pre-registers metrics, estimates resource use, and treats hardware execution as a measured experiment.

Teaching move

Give two unlabeled result plots from nominally the same circuit and ask which is 'better.' Then reveal that no backend, shots, date, mapping, or uncertainty was recorded. The class should conclude that the question is under-specified.

In-class discussion

Ask students to make a prediction first, defend it in plain language, and identify what observation would prove their prediction wrong. Then connect the qualitative argument to the mathematical model used in this chapter.

Worked example

Define Bell-state matched-outcome probability as the metric. Preserve the exact logical circuit, compile separately for each approved target, record all metadata, run a fixed shot count, and compare against an ideal baseline. Interpret the result with uncertainty and compilation differences in mind.

How to reason about the result

Separate three layers: (1) the ideal mathematical prediction, (2) finite-shot sampling, and (3) implementation effects such as noise or compilation. A good laboratory report identifies which layer can plausibly explain an observed discrepancy.

Check your understanding

  2. Name five pieces of metadata needed for reproducibility.
  3. Explain the difference between reproducing a result and extending it.
